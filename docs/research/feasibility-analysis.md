# Secret Wards feasibility comparison

The working budget is **24 total person-hours across two people**, including the brief and final integration. That is an interpretation of the team’s reply. The official runtime is 2 CPU cores, 4 GB peak process-tree RSS, and 900 seconds, with network access available only at setup and no GPU or LLM. No candidate tool was installed or benchmarked in this investigation. Ranges below estimate incremental prototype effort once fixtures and interfaces exist, and exclude full integration. ## Detection and identity resolution

| Candidate | Advantages and compatibility | Trade-offs and cost | Effort estimate and validation gate |
|---|---|---|---|
| Context and field-role rules plus Unicode normalization | Extends the current Python pipeline. Excellent traceability and local processing. Can use format and role clues to handle invented names. | Requires representative role fixtures and careful separation of original and normalized text. Label-only rules can miss new language. CPU and RAM use should be modest on bounded inputs. | 2–4h for a prototype. Demonstrate broader role recall on unfamiliar labels without losing dose, complaint, or clinician text. |
| Selected parser and similarity helpers for phones, Indic scripts and fuzzy comparison | Local libraries address distinct, testable problems. Can enrich the detection and linkage view without altering clinical text. | A valid phone-shaped value may represent another quantity. Transliteration can add ambiguity. Fuzzy comparison needs scoped inputs and an offline wheel and license check. | 2–4h for a focused spike. Evaluate changed recall on names and digits, homonym collisions, and installability on the target Linux setup. |
| Presidio custom recognizers or an equivalent NLP framework | Reusable span and recognizer interfaces. Suitable for local use if the configured backend and assets are bundled. | Extra configuration and transitive dependencies. Hindi and Hinglish behavior depends on the custom recognizers and selected language backend. Integration work can overlap with a small custom layer. | 3–6h for a slice. Compare with direct Python rules on the same fixtures and account for setup and deployment time. |
| Local CRF or character-feature model | Can learn cues missed by hand-coded rules. Small locally trained model is compatible in principle with the model constraints. | Needs span training data and leakage-resistant splits. Annotation format, training, and evaluation can dominate the window. Additional model provenance and files to carry. | 6–10h for a narrow comparison after labels exist. Treat as stretch unless one team member already has a training and evaluation workflow. |
| Deterministic anchors with bounded fuzzy comparison and group conflicts | Simple to inspect. Hospital-issued IDs can be scoped to issuers and strong evidence can be checked before fuzzy matching. Good fit for abstention and an in-memory prototype. | Weak fragments may remain unresolved. Shared values and transitive joins can still cause false merges. Candidate growth depends on block skew. | 3–5h for a narrow spike. Include shared-contact, reused-ID, contradictory-cluster and cross-script pairs. Log only aggregate counts. |
| Fellegi–Sunter with Splink or a classical linkage package | Established probabilistic method can combine incomplete feature evidence and provide tunable thresholds. Local backend available for structured feature tables. | Needs calibrated evidence and conflict-aware cluster construction. A trained score cannot compensate for missing extracted fields. Backend and temporary-storage behavior add validation work. | 5–9h after feature extraction exists. Compare pair and cluster precision at equal recall and measure peak RSS with skewed blocks. |

Licenses, specific packages, platform requirements and primary sources are recorded per tool in the [technology survey](tools-and-technologies.md). Estimates in the matrix are project hypotheses.

## Privacy, formats, and runtime choices

| Candidate | Advantages and compatibility | Trade-offs and cost | Effort estimate and validation gate |
|---|---|---|---|
| Uniform age and location coarsening plus a consistent per-patient date shift | Simple and explainable. Date intervals remain exact when the same offset applies to supported dates. Easy to compare against starter helpers. | Fixed policy can over-generalize common records and still leave unusual profiles identifiable. Date parsing, partial dates, uncertain links and structured types require explicit handling. | 2–4h for selected fields. Check exact clinical intervals and age truth, then measure uniqueness and retained precision on the same synthetic releases. |
| Selective privacy policy guided by patient-level rarity | May broaden only exposed groups and preserve more useful detail. Useful as a comparison point on the unfamiliar cases. | Needs a trustworthy identity view, an explicit field policy, group-size support, and checks for cohort bias. Privacy response depends on what the synthetic risk measure observes. | 4–7h on a few fields. Pursue only after a fixed policy works and there is a measurable change at a comparable utility level. |
| Format-specific JSON/FHIR policies plus local R4 validation | Fits the existing format-preserving contract and gives a direct way to detect broken IDs, references and dates. | Reference edits and attachment handling can be complex. Full validators may add Java or other setup and memory costs. A dev-only validator limits submission runtime dependencies. | 3–6h for a representative Bundle and supported field set. Require actual R4 version, resolvable references and intact clinical content before widening coverage. |
| Bounded two-pass batch or segmented streaming | A first pass can collect compact evidence before linkage and a second can write from read-only input. Record-scale memory can be compared with per-file parsing. | More I/O and more state to reconcile. Disk-backed indices add confidentiality, cleanup, and consistent-key requirements. The starter's practice sample is too small to validate scaling. | 3–6h for a representative stress slice. Track input size, candidate count, RSS and total time before choosing an intermediate store. |
| Quarantine/report with defensive format checks and no raw copies | Strong fit for malformed and unsupported data. Limits unnecessary raw storage. Central reason codes are testable. | Scores can fall if viable clinical files are discarded. Parser disagreement and false classifications need tests. | 1–3h for a narrow set of malformed fixtures. Reconcile every file and show protected data remains absent from communications and artifacts. |
| Offline OCR or deeper parsing for optional attachments | Might recover more clinical coverage in supported scans. Local engines can run without an API. | OCR errors in Indic text and numerics can compromise both privacy and fidelity. Model files, CPU time, and the release format all need verification. | 5–9h for a meaningful comparison. Defer unless the team can show significant input coverage and validate output safety. |
| Aggregate-only release, differential privacy for statistical products, or a controlled query enclave | Useful external approaches if researchers can work with a different access or output model. | Fundamental mismatch with the judged file-preserving, patient-level output. Implementing a query service adds access control, policy and operating costs. | Relevant to the design discussion. No submission prototype proposed under the current contract. |

Comparisons draw on the organizer's output constraints and the primary-source technology and release-policy research. The effort, coverage, and resource estimates require measurement. ## Packaging and budget

| Option | Fit and resource implications |
|---|---|
| Existing Python runner with only selected dependencies | The starter's dependency-free baseline ran locally. Each candidate native wheel, model asset, and resource file still needs clean Linux setup and offline verification. Reusing the interface minimizes packaging changes. |
| A different runtime such as Go, Java, or Rust | The manifest permits it. A mature local FHIR validator may justify an auxiliary tool for development. Rewriting the main pipeline would consume format and integration time and needs a team-specific advantage. |
| Hosted API or hosted model | Can be relevant to comparable real-world work, but an internet dependency violates contest runtime rules. Generative model use in the pipeline is also disallowed. |

A provisional capacity split reserves **5–6 of 24 person-hours** for end-to-end testing, packaging and communicating the result. One person can own contracts, data formats and release checks while the other owns detection and linkage evidence. Shared fixtures, a small interface and early end-to-end testing are dependencies for that arrangement. The remaining hours support selective spikes within the ranges above. These are budget assumptions and do not settle ownership or implementation scope. [User decisions and open constraints](open-questions.md)

## Experiments for the prototype phase

| Experiment | Evidence to collect | What a result would unlock |
|---|---|---|
| **Unfamiliar role-and-format fixtures** | Compare two detector configurations on fresh synthetic names, script shifts, novel headers, separated digits, and matching clinical negatives. Report recalls and retained protected spans by scenario. | Determine whether format context, normalized spans, or learned features justify their integration cost. |
| **Linkage conflicts and abstention** | Compare anchors alone with bounded similarity and a conflict check using synthetic homonyms, shared contacts, local ID reuse, fragments and contradictions. Report pair precision, F0.5, false merges and abstention. | Establish a safe evidence threshold and judge whether statistical linkage is worth its complexity. |
| **Privacy–utility comparison** | Measure input-based clinical and record retention, cohort distribution, temporal fidelity and approximate patient-level uniqueness across no transformation, fixed broadening and selective broadening. Use the same cohorts for each. | Compare fixed and adaptive policies without conflating record suppression with improved privacy. |
| **Contract and channel check** | Use synthetic nested keys, duplicate files, known pseudonyms, malformed structures and one representative FHIR Bundle. Verify pointers, reference resolution, release directories, captured logs and artifact counts. | Establish which platform and output adaptations are safe and identify organizer-dependent decisions. |
| **Scale and repeatability** | Run bounded synthetic stress fixtures at multiple sizes under matching Linux limits. Record CPU, process-tree RSS, time, sorted output and exact bytes across two same-secret and one changed-secret run. | Validate bounded processing and determine if a second pass, consolidated parsing, or disk-backed storage is justified. |

Use aggregates for experiment reporting. All fixtures should be synthetic, and variants that inform a design choice should be kept separate from ones used repeatedly for tuning. No benchmark or official-score prediction has been recorded for the candidate approaches.
